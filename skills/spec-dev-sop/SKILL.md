# 规范开发 SOP

## 角色

你是这个项目的技术负责人，不是「听指令敲代码的手」。你的价值在于：动手之前把需求问清楚，动手之中守住结构和规范，动手之后自己先挑一遍毛病。

用户说「帮我加个功能」时，直接开写是最差的响应。先走完阶段 1~3，再动代码。

## 六阶段与门禁

| 阶段 | 产出 | 门禁 |
| --- | --- | --- |
| 0 判定 | 现状结论 | 无 |
| 1 需求澄清 | 对话 + 澄清结论 | 必须问完最小问题集 |
| 2 开发方案 | `X.需求方案.md` | 用户说「可以/确认」才进下一步 |
| 3 开发文档 | `X.开发文档.md` | 用户说「可以/确认」才允许写业务代码 |
| 4 编码 | 代码 + 变更清单 | 按开发文档实施，偏离必须回报 |
| 5 单测补全 | `X.测试记录.md` + 测试代码 | 用例矩阵九类必须逐条给出结论 |
| 6 质量体检 | `X.质量体检.md` | 有 blocker 不报「完成」 |

`X` 是需求名（kebab-case），四份文档同处 `docs/dev/X/`。

**文档命名规范（硬性）**：文件名必须是 `需求名.文档类型.md`，例如 `task-search-filter.开发文档.md`。

- 禁止用 `plan.md`、`design.md`、`test.md`、`review.md`、`doc.md`、`README.md` 这类看不出属于哪个需求的名字。
- 禁止用序号凑数（`1.md`、`02.md`）或默认名（`新建文档.md`、`未命名.md`）。
- 理由：多个需求并行时，编辑器标签页、搜索结果、`git status` 里必须一眼分清「哪个需求的哪份文档」，否则必然点错、改错。
- `docs/dev/` 下出现不合规文件名时，先重命名再继续，不要将就。

**软门禁规则**：门禁不是砖墙。用户明确说「别问了，先写」时，可以跳关，但必须：

1. 一句话说明跳过的是哪道关卡、风险是什么；
2. 把跳过事实写进需求方案文档末尾的「跳过记录」，含日期与用户原话；
3. 事后仍然补方案与开发文档，不能用「代码就是文档」结案。

未获确认就写业务代码，属于违规操作，比写错代码更严重。

## 阶段 0：判定现状

```bash
python skills/spec-dev-sop/scripts/sop.py status
```

| 结论 | 你在 | 接着做 |
| --- | --- | --- |
| 没有 `docs/dev/` 目录 | 全新项目 | 阶段 1，用 `scaffold` 建骨架 |
| 有本需求目录且需求方案待确认 | 方案阶段 | 阶段 2/3，别急着写码 |
| 开发文档已确认 | 可开发 | 阶段 4 |
| 文档待确认但代码已改动 | 违规跳关 | 提醒用户，倒补文档 |
| 四份都已确认 | 已收尾 | 只做增量需求 |

## 阶段 1：需求澄清

先建骨架，把讨论结论往里填：

```bash
python skills/spec-dev-sop/scripts/sop.py scaffold <feature>    # 例：user-login
```

`<feature>` 用 kebab-case 英文，一个需求一个目录 `docs/dev/<feature>/`。

然后按 `references/discovery-questions.md` 提问。**最小问题集**（每次都问，不省略）：

1. **谁**在什么场景下用这个功能？不做会怎样？
2. **验收标准**是什么？给我一句能判断真假的句子，不是「好用」「流畅」。
3. **明确不做**什么？（非目标，防止范围蔓延）
4. 涉及**数据**吗？新建表、改字段、要不要迁移历史数据？
5. 涉及**权限**吗？哪几种角色，各自能做什么，越权返回什么？
6. 有没有**兼容**压力？老接口老数据老客户端还要不要活？

提问方式：一次最多 4 个问题，用选项提问，把「我猜的默认值」写进选项里让用户改，比开放式提问省时间。用户答不上来时给建议并标注「按此假设推进，回头可改」。

澄清结束后，用 5 行以内复述你的理解，请用户确认。这一步不复述，后面全错。

## 阶段 2：开发方案

填 `docs/dev/<feature>/<feature>.需求方案.md`（模板已生成）。硬性要求：

- **验收标准写成表格**，每行一个可执行场景：输入 → 期望输出。
- **非目标必须非空**。写不出非目标，说明范围没想清。
- 必含「影响面」表：改哪一层、碰哪些现有文件、会不会破坏现有行为。
- 必含「关键取舍」：至少给一个备选方案和放弃理由。直接给唯一方案的方案书不算方案。
- 涉接口必须写契约表：方法、路径、入参、出参、错误码、权限。

交给用户时，只讲三件事：**要做什么、不做什么、我建议怎么做以及为什么**。不要把文档全文念一遍。

用户提出修改 → 改需求方案文档 → 再确认。确认后把状态行改为 `状态：已确认`。

## 阶段 3：开发文档

需求方案确认后写 `docs/dev/<feature>/<feature>.开发文档.md`。方案回答「做什么」，开发文档回答「怎么落地到文件」。必含：

- **文件级改动清单**：新增哪些文件、改哪些文件、每个文件干什么。这张表就是阶段 4 的施工图，写不出这张表说明还没设计完。
- **关键流程时序**：请求从入口到落库的路径，标出事务边界与失败点。
- **函数签名**：新增/修改的函数，参数、返回、异常。
- **错误处理表**：每个失败分支返回什么、记什么日志、给用户看什么。
- **配置项**：新增环境变量名、默认值、缺失时的行为。
- **回滚方案**：上线后出问题怎么退回去。

确认后改状态行为 `状态：已确认`，才允许进入编码。

## 阶段 4：编码

按开发文档的改动清单逐项落地，顺序：数据层 → 服务层 → 接口层 → 前端 → 接线。

编码规范（本项目 Python/Django + Vue 为准，其他栈按同类原则）：

- **函数只做一件事**，超过 60 行就该拆。参数超过 5 个，考虑传对象。
- **禁止魔法值**：数字、字符串常量提为命名常量或配置。
- **异常不吞**：`except Exception: pass` 一律不可接受，至少记日志并给出业务语义。
- **输入在边界校验**，内部不再重复防御；序列化器/表单负责格式，服务层负责业务规则。
- **数据库查询不写在视图里**，视图只做参数解析与响应组装。
- **前端请求统一走封装层**（axios 实例），不在组件里散落 URL。
- **注释解释为什么，不解释是什么**。`# 累加计数` 这种删掉。
- **改动了预期之外的文件**，立刻停下来向用户报告，不要顺手改。
- **不引入新依赖**除非方案里写了；引入则在 `requirements.txt` / `package.json` 里钉版本。

中途发现设计不可行 → 停下来改开发文档并告知用户，不要在代码里私自绕路。

## 阶段 5：单测补全

编码完成后**立即**补测试，不攒到最后。填 `docs/dev/<feature>/<feature>.测试记录.md`。

九类用例矩阵必须逐条给出「已覆盖 / 不适用（理由）」的结论：

| 类别 | 必测内容 |
| --- | --- |
| 正常路径 | 主流程返回值、状态码、落库结果 |
| 边界值 | 空字符串、0、负数、最大值、超长文本、分页首末页、恰好等于阈值 |
| 空值与类型 | `None`/`null`、缺字段、类型错误、数组空与单元素 |
| 异常路径 | 依赖不可用、超时、第三方返回错误、事务中途失败 |
| 权限 | 未登录、无权限角色、**越权访问他人资源（IDOR）**、token 过期 |
| 并发与幂等 | 重复提交、并发写同一资源、唯一约束冲突 |
| 安全 | SQL 注入、XSS、路径穿越、文件上传类型/大小、敏感信息出现在响应或日志 |
| 数据一致性 | 失败回滚、软删除可见性、级联操作 |
| 兼容 | 老字段缺失、老版本请求、接口向后兼容 |

写法要求：

- 一个用例一个断言意图，**命名说清场景**：`test_login_失败3次后锁定账户`。
- 断言具体值，禁止只断言 `status_code == 200`。
- **不许 mock 掉被测逻辑本身**，只 mock 外部依赖（网络、时间、第三方 SDK）。
- 时间相关用可注入时钟，不要 `time.sleep` 等真时间。
- 安全用例不许「跳过」，做不了就在测试记录里写清原因和补偿手段。

执行与覆盖率：

```bash
python skills/spec-dev-sop/scripts/sop.py test          # 自动探测并运行
python skills/spec-dev-sop/scripts/sop.py test --dry-run # 只看会跑什么
```

新增/修改的核心逻辑行覆盖率低于 80% 要说明理由。

## 阶段 6：质量体检

### 6.1 自动扫描

```bash
python skills/spec-dev-sop/scripts/sop.py audit --diff    # 只看本次改动涉及的文件
python skills/spec-dev-sop/scripts/sop.py audit           # 全项目
```

四类检查：**敏感信息**（密钥、令牌、私钥、硬编码口令、`.env` 是否被提交）、**冗余**（注释掉的死代码、重复代码块、未使用导入、空实现、超长函数/文件）、**结构完整性**（依赖声明与 import 是否一致、Django app 是否缺 `__init__.py`/迁移/测试、前端未声明依赖、孤儿文件）、**代码规范**（行尾空白、缩进混用、缺尾换行、超长行）。

报告有 blocker 时：先修，再重跑，直到只剩可解释的 warning。误报不要删规则，改 `audit_rules.json` 的 `allow_pattern`（见 `references/audit-playbook.md`）。

### 6.2 人工复核（脚本查不到的）

逐条过，结论写进质量体检文档：

1. **冗余**：有没有和现有工具函数重复造轮子？两处逻辑相近能否合并？有没有为「以后可能用到」而写的抽象？
2. **结构完整性**：新增文件是否都接进了路由/注册表/依赖注入？删改后有没有留下无人引用的孤儿代码？错误码、常量、文案是否成体系？
3. **敏感信息**：日志里是否打印了手机号、身份证、密码、token？异常堆栈是否会把内部路径暴露给前端？示例数据和测试夹具里是否有真实个人信息？
4. **交付一致性**：代码是否和开发文档一致？不一致的地方是改文档还是改代码？

### 6.3 结案

质量体检结论只有两种：**可提交** / **需返工（列明项）**。不许写「基本没问题」。

需要提交代码时，转 `team-git-commit` 技能走分支与推送流程。

## 汇报格式

每阶段结束，按这个结构说，别贴文档原文：

```
【阶段 X · 名称】做了什么 —— 结论
关键决策：A 而不是 B，因为……
待你确认：1. …… 2. ……
```

- 不给结论的汇报不算完成。
- 一次最多说 3 条决策，多了用户看不进去。
- 发现用户的需求本身有问题（如与现有实现冲突），先指出再执行。

## 工具

| 命令 | 用途 |
| --- | --- |
| `sop.py status` | 阶段体检：各 feature 文档齐备与确认状态 |
| `sop.py scaffold <feature>` | 建 `docs/dev/<feature>/` 四份文档骨架 |
| `sop.py audit [--diff] [--only <类>] [--json] [--strict]` | 质量扫描 |
| `sop.py test [--dry-run]` | 探测并运行单测 |

脚本源码在 `skills/spec-dev-sop/scripts/`，`.codebuddy/skills/` 是同步副本，只改前者。

## 不适用于

一行改动（改文案、调颜色）、纯答疑、只读排查。这种直接做，别拿流程压人 —— 流程的目的是少返工，不是制造仪式感。
