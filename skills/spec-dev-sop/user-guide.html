规范开发使用说明

这套流程只为一件事服务：少返工。动手前把需求问清楚、把方案写下来，动手后自己先挑一遍毛病。你要做的决策只有几个，其余步骤助手会带着走。

适用对象：团队全体成员 触发方式：说一句「开始做 XX」 版本：2026-11

为什么要有流程 必读

代码写错的代价，远小于「做错东西」和「改错地方」的代价。流程卡在动手之前，就是为了把这两类返工挡在成本最低的时候。

随便写现在的常见情况

需求一句话就开工，写着发现理解错了；改完不知道影响了谁；提交前没人看过，上线才发现越权。

返工发生在最难改的时候。

走流程这套 SOP

先问清六件事，写成方案给你确认；开发文档写明改哪些文件；写完补边界与安全用例；最后机器扫一遍。

返工发生在只改文档的时候。

流程不是仪式感。一行改动（改文案、调颜色）、纯答疑、只读排查不需要走这套流程，直接做就行。

六个阶段

每个阶段都有明确的产出文件，确认过的文件会标上「已确认」。没确认就写代码，属于跳关。

0

判定现状

先看这个需求处在哪一步，避免在方案阶段就动手写码。

产出：一句话结论（新需求／方案待确认／可开发／已收尾）
1

需求澄清

必问：谁用、验收标准、明确不做什么、涉及数据与权限吗、兼容压力、什么时候要。

产出：对话记录 + 5 行以内的复述确认
2

开发方案

验收标准写成表格，非目标必须非空，给备选方案和放弃理由。

产出：需求名.需求方案.md　门禁：你说「可以」才能进下一步
3

开发文档

方案回答「做什么」，这一步回答「落到哪些文件」：改动清单、时序、函数签名、错误处理、回滚方案。

产出：需求名.开发文档.md　门禁：确认后才允许写业务代码
4

编码

按改动清单施工。改到预期之外的文件要立刻停下来报告，不许顺手改。

产出：代码 + 实际改动清单
5

单测补全

九类用例逐条给结论：正常、边界、空值、异常、权限、并发、安全、一致性、兼容。

产出：需求名.测试记录.md + 测试代码
6

质量体检

机器扫四类问题，人工复核机器看不出的：重复造轮子、结构断裂、日志泄露、文档与代码不一致。

产出：需求名.质量体检.md　有 blocker 不许报「完成」

门禁是软的。你明确说「别问了，先写」时，可以跳关，但必须在需求方案里留下记录：跳过哪道关卡、为什么、你的原话、风险是什么，事后仍然要补文档。不能拿「代码就是文档」结案。

前三阶段：出方案

你要做的只有两件事：答清楚问题，然后说「可以」或「不对，改成……」。

会先建骨架

python skills/spec-dev-sop/scripts/sop.py scaffold user-login

这会创建docs/dev/user-login/下的四份文档。需求名用英文小写加连字符，别用中文和空格。

提问方式

助手一次最多问 4 个问题，并且会把「我猜的默认值」写进选项里，你只需改不对的地方。答不上来时会给出建议并标注「按此假设推进，回头可改」。

你要重点看的三处

看什么为什么
验收标准表每行必须是「给什么输入 → 期望什么结果」，写不出表格说明需求没想清
非目标写了「无」就是没想过范围，后面一定膨胀
关键取舍只给一个方案、没有备选和放弃理由的，不算方案

确认时把状态行改成状态：已确认。要求修改就直接说，文档改动比代码改动便宜得多，这正是把门禁放在这里的原因。

写代码

这一阶段你基本不用管，但如果有下面这些情况，助手会主动打断你。

施工顺序

数据层 → 服务层 → 接口层 → 前端 → 接线。顺序错了容易出现「前端先写死假数据，最后来不及接」。

会被拦下的行为

行为原因
改到设计之外的文件影响面没评估，容易踩坏别人负责的部分
把数据库查询写进视图分层破坏，后面没法复用和测试
吞异常（except: pass）线上出问题没有任何线索
凭空引入新依赖方案里没写就加，等于偷偷扩大范围
发现设计不可行却自己绕路代码和文档对不上，下次没人敢改

中途发现方案走不通，正确做法是停下来改开发文档并告诉你，不是在代码里私自换条路。文档骗人比代码有 bug 更麻烦。

补单测

编码完成后立即补，不攒到最后。九类用例必须逐条给出「已覆盖」或「不适用（理由）」，空着等于没做。

类别必测内容
正常路径主流程返回值、状态码、落库结果
边界值空串、0、负数、最大值、超长文本、分页首末页、恰好等于阈值
空值与类型None／null、缺字段、类型错误、空数组与单元素
异常路径依赖不可用、超时、第三方报错、事务中途失败
权限未登录、无权限角色、越权访问他人资源（IDOR）、token 过期
并发与幂等重复提交、并发写同一资源、唯一约束冲突
安全注入、XSS、路径穿越、上传类型与大小、敏感信息外泄
数据一致性失败回滚、软删除可见性、级联操作
兼容老字段缺失、老版本请求、接口向后兼容

写法底线

  • 一个用例一个断言意图，命名说清场景，例如test_非法状态值返回400并说明原因
  • 断言具体值，不许只断言status_code == 200
  • 不许 mock 掉被测逻辑本身，只 mock 外部依赖
  • 时间相关用可注入时钟，不写sleep等真时间

覆盖率是下限不是目标。100% 覆盖率照样可以漏掉越权。新增核心逻辑行覆盖率低于 80% 要写明理由。

质量体检

机器查可机械判定的，人查需要判断的。两者都做完才算体检结束。

机器查四类

类别查什么
敏感信息硬编码口令与密钥、私钥、带密码的连接串、各类 token、身份证与手机号、硬编码 IP、.env是否被提交
冗余被注释掉的死代码、跨文件重复代码块、未使用的 import、超过 60 行的函数、只有pass的空实现
结构完整性import 与依赖清单是否一致、Django app 缺迁移或测试、DEBUG=True、文档命名是否合规
代码规范超长行、行尾空白、缺尾换行、Tab 与空格混用、BOM

报告怎么读

级别含义怎么处理
blocker泄露、崩溃、语法错误级必须修，修完重跑
warning大概率的真问题逐条判断，是真问题就修
info提示与风格扫一眼，本次不处理就记进遗留项

有 blocker 时命令返回 1；加--strict时 warning 也返回 1。

人查五件事

  1. 业务语义冗余：自己写了格式化函数，而项目里早有一个
  2. 抽象过度：只调用一次的中间层、为「以后可能扩展」加的基类
  3. 结构断裂：新增文件没接进路由、删了逻辑但常量文案没跟着删
  4. 分层破坏：视图里写聚合 SQL、组件里直接拼 URL
  5. 交付一致性：代码与开发文档不一致却没回写文档

误报不许改代码去迎合，也不许删规则。正确做法是给规则加allow_pattern或exclude_glob，把「本项目中合法的写法」写进规则里。规则集是活的，越用越准。

文件放哪、怎么命名

一个需求一个目录，四份文档。文件名必须能一眼看出属于哪个需求，否则多个需求并行时标签页和搜索结果全是重名。

docs/dev/task-search-filter/
  task-search-filter.需求方案.md
  task-search-filter.开发文档.md
  task-search-filter.测试记录.md
  task-search-filter.质量体检.md
规则说明
格式需求名.文档类型.md，点分，四段类型固定
禁止plan.md、design.md、test.md、review.md、doc.md、未命名.md
禁止用序号凑数（1.md、02.md）
校验体检会检查docs/dev/，不合规直接报 warning

为什么较真：四个需求并行开发时，编辑器标签页、全文搜索、git status里全是plan.md，必然点错、改错。这一条是返工过才定下来的。

两种用法

交给助手，或者自己敲命令，两条路都通。助手做的每一步，你自己也能复现。

推荐交给助手

直接说需求，助手按阶段推进，每阶段只汇报三件事：做了什么、关键决策、要你确认什么。

帮我做一个任务搜索功能

需要打断时说「先别问，直接写」或「这里改成……」，门禁会尊重你的选择并留痕。

自己来敲命令

四步走：建骨架、看阶段、跑测试、做体检。

sop.py scaffold <需求名>
sop.py status
sop.py test
sop.py audit --diff

audit --diff只扫本次改动，日常用这个；audit不带参数是全项目基线，适合季度体检。第一次在本项目跑全量可能会看到一批历史问题，那些不属于本次改动。

常见问题

问题怎么办
小改动也要走六步吗？ 不用。改文案、调颜色、只读排查直接做。判据是：会不会动接口、数据或权限，不动就走简化路子
我不想看文档，只想赶紧写 说「先写，文档后补」。会跳关但留痕，写完必须倒补方案与开发文档，不许拿代码当文档
体检报了一堆 warning 先逐条看是不是真问题。是误报就改audit_rules.json加豁免，不要改业务代码去迎合规则
项目没有测试框架，还能补单测吗？ 能。Python 用 Django TestCase 或pytest；前端没装 vitest 时，可把逻辑抽成纯函数用node --test零依赖跑
测试连不上 MySQL 加一份config/settings_test.py继承主配置、只把数据库换成内存 SQLite；sop.py test会自动带上它
文档名写错了 直接改名，别将就。status和audit都认需求名.类型.md
需求做到一半要改方案 改需求方案文档，重新确认。已经写了的代码不用回退，但要同步改开发文档
体检结论写什么算合格 只有两种：可提交或需返工（列明项）。写「基本没问题」视为没做完

命令速查表

脚本在skills/spec-dev-sop/scripts/，只依赖 Python 标准库，不用装任何东西。

命令用途
sop.py status看所有需求处在哪个阶段，含是否跳关
sop.py scaffold <需求名>建docs/dev/<需求名>/四份文档
sop.py audit --diff只体检本次改动（日常用）
sop.py audit全项目基线体检
sop.py audit --only secrets只查某一类，可选secrets/debug/redundancy/structure/style
sop.py audit --json机器可读输出，便于接 CI
sop.py audit --strictwarning 也算失败，退出码非零
sop.py test自动探测并运行后端与前端测试
sop.py test --dry-run只看会跑哪些命令，不执行

规则怎么迭代

所有检查项都在scripts/audit_rules.json里，加规则不用改代码：

{
  "id": "my-rule",
  "severity": "warning",
  "langs": ["python"],
  "skip_tests": true,
  "pattern": "你的正则",
  "allow_pattern": "压制误报的正则",
  "message": "人话说明怎么修"
}

改完执行python skills/sync_skills.py同步，再重启会话让技能重新加载。
