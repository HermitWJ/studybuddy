# Git 协作原理速查（讲解用）

引导时按这里的口径讲，不要临场发明类比。每条都给了「一句话定义 + 为什么 + 可以怎么打比方 + 什么时候讲」。

## 仓库、远程、本地

- **一句话**：本地仓库是你电脑上的一份完整副本；远程（origin）是 GitHub 上的那份，大家以它为交汇点。
- **为什么**：先提交到本地，再推送到远程。本地是私人的草稿本，远程是共享的公告板，推上去别人才能看到。
- **打比方**：本地像你桌上的草稿，`push` 是把它贴到公告板上；`fetch` 是把公告板上的新内容抄回来。
- **什么时候讲**：她第一次问「提交了别人能看到吗」。

## 分支

- **一句话**：分支是仓库的一条平行时间线，互不影响。
- **为什么**：同一个仓库里，你的半成品不该干扰别人，分支就是隔离带。
- **打比方**：一栋楼的不同装修方案，各自施工，验收合格才合并到公共区域。
- **什么时候讲**：开工阶段，解释为什么不是所有人都在 main 上改。

## 为什么每人一条 feat/<用户名>

- **为什么**：三条理由 —— 隔离（你写坏了不影响别人）、可回溯（一条线对应一个需求）、可评审（PR 只针对一条线）。
- **补充**：个人分支是私有分支，所以可以随意 rebase 改写历史；main 是公共分支，历史不能改。
- **什么时候讲**：开工阶段，第一次需要讲清楚。

## 提交（commit）

- **一句话**：一次提交 = 一组改动的快照 + 一条说明。
- **为什么**：它是回滚的最小单位。将来某次改动出问题，能单独撤销这一次而不影响其他。
- **建议粒度**：一个提交只做一件事。修 bug 和重构代码不要混在一个提交里。
- **什么时候讲**：第一次提交前，顺便给出拆分建议。

## 领先 / 落后

- **一句话**：领先 = 你本地有 main 没有的提交；落后 = main 有你没有的提交。
- **为什么**：落后就必须同步，否则你是在过期代码上做增量，合并时冲突集中爆发。
- **什么时候讲**：`check` 输出「领先 X / 落后 Y」时。

## rebase

- **一句话**：把你自己的提交「剪下来」，重新贴到最新 main 的末尾。
- **为什么**：保证你的改动建立在团队最新成果上，历史保持一条直线。
- **打比方**：你在草稿上写了两段，别人更新了第一章；rebase 是把你的两段沿着新第一章重抄一遍，内容不变但位置更新。
- **关键点**：rebase 会产生新的提交 ID（内容一样、指纹变了），所以推送时需要 `--force-with-lease`。
- **什么时候讲**：开工同步、提交同步时各讲一次，第二次一句带过。

## 为什么不用 merge

- **一句话**：`merge` 会额外产生一个「合并提交」，把两条时间线缝在一起，历史变成网状。
- **为什么**：个人分支上用 merge 同步 main，历史里会反复出现「Merge main into feat/xxx」的噪音提交，`git log` 变乱，定位问题困难。
- **例外**：PR 合并到 main 时由 GitHub 做合并（通常用 squash），那是团队统一行为，个人不要手动 merge main。
- **什么时候讲**：她想「git pull 一下」的时候。

## 冲突

- **一句话**：同一文件的同一块被两边改成了不同内容，git 无法判断保留哪个。
- **为什么**：git 只懂文本，不懂业务。它不猜，停下来问人。
- **标记含义**：`<<<<<<<` 与 `=======` 之间是你的版本，`=======` 到 `>>>>>>>` 是对方的版本。
- **正确态度**：不是「选我的」，而是「看两边意图，写出最终该有的样子」，有时两边都要留。
- **什么时候讲**：第一次遇到冲突时完整讲；之后只提醒「这次是哪两个改动撞了」。

## force-with-lease

- **一句话**：强推的一种安全版本 —— 只有远程分支还是你上次看到的样子时才覆盖。
- **为什么**：rebase 改写了你的提交，普通推送会被拒绝（历史分叉）。`--force-with-lease` 能覆盖，但会先检查别人有没有往里推东西，比 `--force` 安全。
- **边界**：只对自己那条 `feat/<用户名>` 用。对 main 或别人的分支，任何强推都是禁止的。
- **什么时候讲**：脚本提示使用了它的时候。

## Pull Request（PR）

- **一句话**：请求把你的分支合并进 main，并附上 diff 供人评审。
- **为什么**：main 要一直保持可运行。评审 + CI 通过才合并，是团队对「稳定」的最低保障。
- **什么时候讲**：推送成功后给链接时。

## pre-push 钩子

- **一句话**：git 在推送前自动执行的检查脚本，装在本地 `.git/hooks/`。
- **为什么**：在最后一道关口拦住「推 main」这种不可逆操作。钩子只装在你本地，所以每人需要各装一次。
- **什么时候讲**：她试图推 main 被拦时。

## 常见误区

| 她的想法 | 实际情况 |
| --- | --- |
| 「先 pull 一下最新代码」 | 个人分支上应该用 rebase，`pull` 默认会 merge 出多余提交（建议 `git config pull.rebase true`） |
| 「提交了就代表别人能看到」 | 只是本地快照，必须 push 才到远程 |
| 「冲突了就把我的覆盖掉」 | 会丢掉别人的改动，必须看业务语义 |
| 「重置一下远程分支没关系」 | 只对自己的 feat 分支可以，main 和他人分支绝对不行 |
| 「PR 合并了分支就自动变干净」 | 本地分支仍留着旧提交，下次开工要 `start --recreate` 重建 |
| 「改动越攒越完整」 | 一个巨型提交无法单独回滚，评审也没法看 |
