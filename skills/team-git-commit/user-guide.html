团队协作使用说明

你需要记住的只有三件事：开工前同步、写小步提交、合并走 PR。具体操作可以交给助手，也可以自己敲命令，这份说明两条路都写了。

适用对象：团队全体成员 分支规范：feat/你的用户名 版本：2026-11

先记住三条规则 必读

所有流程都是为这三条服务的。理解了原因，操作就不用死记。

  1. 改动只进自己的 feat/你的用户名 分支 每人一条独立时间线，互不干扰。你写坏了只影响自己，别人照常干活。
  2. 动手前先把 main 的最新代码接到自己分支上 你越晚同步，冲突越多。开工时同步，冲突只会在你还没写代码的时候出现，处理成本最低。
  3. 永远不直接推 main，只能提 PR main 要一直保持能跑。别人的代码先进 main，你的工作才不会被别人的问题卡住。

想“图快”直接推 main？先不说评审，本地钩子会直接拦下来，推不上去。这不是限制你，是保护所有人（包括你自己）不被半成品代码拖住。

一次性准备

每台机器只做一次。做完之后，日常只需要“开工”和“提交”两个动作。

1. 克隆仓库

# 克隆到本地，之后所有操作都在这个目录里
git clone https://github.com/HermitWJ/studybuddy.git
cd studybuddy

2. 告诉工具你是谁

这决定你的分支叫 feat/xxx 里的 xxx，请用你的 GitHub 用户名。

python skills/team-git-commit/scripts/team_submit.py set-user 你的GitHub名

如果你的 git 全局配置已经是自己的名字，这一步可以跳过。但显式设置一次更保险，避免分支名变成别人的。

3. 装防误推钩子

python skills/team-git-commit/scripts/install_hooks.py

装完后，一旦你尝试 git push origin main，本地就直接拒绝并告诉你正确做法。钩子只装在你自己的机器上，所以需要每人各装一次。

用助手的同学可以跳过全部三步：只要说一句「帮我初始化团队协作环境」，助手会依次完成并告诉你结果。

每天开工

打开电脑、开始写代码之前，先做这一步。顺序不能反：先确认分支，再同步 main。

用助手 推荐

直接说你想做什么，例如「我要开始做登录功能了」。助手会先看你目前的状态，再列出现有分支问你要用哪条。

自己动手 命令

先看有哪些分支，再开工：

# 看现有分支（含领先/落后提交数）
python skills/team-git-commit/scripts/team_submit.py branches

# 开工：切到你的分支并同步最新 main
python skills/team-git-commit/scripts/team_submit.py start

# 分支还不存在时，确认后加 --create
python skills/team-git-commit/scripts/team_submit.py start --create

什么时候会问你、问什么

情况你看到的问题怎么回答
你还没有自己的分支用已有分支，还是新建 feat/你？「新建一个」
分支已存在直接切过去可以吗？「可以」
分支上次已经合并过要从最新 main 重建吗？「重建吧」（旧分支会自动备份）

「分支已合并」是什么意思？你上次的 PR 合并进 main 了，这条分支的使命结束了。如果继续在上面写，旧提交会被重新贴到 main 上，等于把已经合并的东西再交一遍。所以工具会拦住你，建议重建。

看到「开工就绪」这四个字，才说明同步完成，可以动手写代码了。

写代码的时候

这一段不需要任何人打扰你。只有四件事值得注意。

小步提交，别攒一整天

完成一个能跑的小功能就提交一次。提交是回滚的最小单位——将来某个改动出问题，你能只撤销那一次，而不是把一整天的工作推倒重来。

别切回 main 上改代码

在 main 上改的东西推不上去（钩子会拦），而且会让你的本地状态变复杂。真改了也别慌，让助手帮你把改动挪到个人分支。

中途想同步 main

# 需要工作区干净，否则先提交或暂存
python skills/team-git-commit/scripts/team_submit.py sync

说「帮我同步一下最新代码」也行。同步会把你已有的提交重新接到最新 main 后面，不会丢东西。

不要用 git merge origin/main

merge 会额外生成“合并提交”，把历史变成网状，git log 里一堆噪音。个人分支统一用 rebase（开工和同步命令已经帮你做了）。

提交代码

提交这一步工具会连做三件事：把你的改动做成提交、接到最新 main 后面、推到你自己的远程分支。全程不碰 main。

用助手 推荐

说「帮我提交」。助手会看一遍你的改动，拟一条提交信息给你确认，然后执行。

自己动手 命令
python skills/team-git-commit/scripts/team_submit.py \
  submit -m "feat(auth): 增加登录接口"

提交信息怎么写

格式：类型(模块): 一句话说明为什么改。标题不超过 72 个字符，别用句号结尾。

类型用在什么改动例子
feat新增功能feat(auth): 增加登录接口
fix修 bugfix(task): 修正分页越界
docs只有文档docs: 补充部署说明
refactor重构，行为不变refactor(core): 抽出公共校验
test只有测试test(auth): 补登录失败用例
chore杂活、依赖、配置chore: 升级依赖版本

不要写「update」「修改」「提交一下」这类话。三个月后（很可能是你自己）看到这条记录，需要知道它到底动了什么、为什么动。

退出码代表什么

退出码含义你要做的
0成功，已经推送到你的远程分支去开 PR
2需要你确认分支（不存在，或已合并需重建）回答助手的问题
3有冲突，没有推送按下一节处理
1其他流程问题看提示文字修正后重跑

遇到冲突

冲突不是错误，是 git 在说「这里我不该替你决定」。它只发生在：你和别人改了同一个文件的同一块内容。

你会看到什么

# StudyBuddy

<<<<<<< HEAD
基础工程，已接入 MySQL。
=======
基础工程，已接入 Redis 缓存。
>>>>>>> a29ab34 (docs: 补充缓存说明)

<<<<<<< 到 ======= 之间是你的版本；======= 到 >>>>>>> 之间是 main 上别人的版本。

怎么处理

  1. 先读懂两边各自想表达什么 不要机械地选「我的」。很多时候两边的改动都对，应该合并成一句。
  2. 把这段改成你最终想要的样子 删掉三行标记，留下正确内容。这个判断是业务判断，只能你来做。
  3. 标记为已解决并继续 命令见下，或者直接说「我改好了」让助手接手。 
# 处理完冲突后
git add 冲突的文件
git rebase --continue

# 然后重跑同一条提交命令，冲突解决了才会推送
python skills/team-git-commit/scripts/team_submit.py submit -m "docs: 补充缓存说明"

为什么冲突没解决就不让推？因为一旦推上去，别人拉到的是带 <<<<<<< 标记的坏代码，整个项目立刻跑不起来。工具会在推送前拦住。

实在处理不下去，先 git rebase --abort 回到冲突之前，再找人一起看。别硬撑着乱删代码。

提交之后

推送成功只是把代码送到了你自己的远程分支，还没进 main。

  1. 开 Pull Request 推送成功后终端或助手会给一个链接，点开就是 PR 页面。标题沿用提交信息的风格，描述写清：改了什么、为什么改、怎么验证。
  2. 等评审 至少一位同事看一遍。有人提意见就继续在自己分支上改、再推送，PR 会自动更新。
  3. 合并后删掉远程个人分支 GitHub 上合并时勾选 delete branch，或让助手处理。分支留着下次会干扰开工判断。
  4. 下次开工记得重建 合并后本地还留着旧提交，开工时工具会提示「分支已合并」，同意重建即可，旧状态自动备份。

PR 的意义：main 一直保持可运行。别人随时能拉最新代码继续干活，不会被你的半成品卡住。

常见问题

按“你看到的现象”查，不用记命令。

你遇到的原因怎么办
提示「分支不存在，需要新建」 你还没有 feat/你 分支，工具不会自己建 确认后加 --create，或跟助手说「新建一个」
提示「分支上的提交都已并入 main」 上次 PR 已合并，分支是残留 加 --recreate 重建（旧分支自动备份）
push 被拒，提示 non-fast-forward 同步后历史被改写，与远程不一致 这是正常的，用 submit 提交即可（它会用带保险的强制推送）
push 被拒，提示「禁止推送到 main」 本地钩子在拦你 改推自己的 feat 分支，合入 main 走 PR
分支叫 feat/别人的名字 用户名没配对，回退成了 git 全局名字 跑一次 set-user 你的GitHub名
提示「上次 rebase 还没收尾」 之前冲突没处理完 解决后 git rebase --continue，或 git rebase --abort 放弃
提示「工作区有未提交改动」 有文件改了没提交 先提交（加 -m 让工具代做），或 git stash 暂存
提示「拉取远程失败」 网络或权限问题 检查网络和 GitHub 登录；体检（check）可以先用本地数据继续
